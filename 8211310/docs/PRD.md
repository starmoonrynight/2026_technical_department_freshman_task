## 1. 产品定位

### 1.1 一句话

同学自愿发布「我丢了什么」（lost）和「我捡到什么」（found）；平台负责**搜索、自动匹配、通知、记录**这四件事，双方通过帖子里的联系方式**自行线下沟通和归还**。

### 1.2 五条定位原则（产品的宪法）

这五条不是愿景口号，每一条都直接决定了某个功能存在或不存在。后面第 9 节的「范围外清单」全部由它们推导得出。

1. **平台只记录事实，不做任何裁决。** 「谁解锁过联系方式」「谁提交了归还确认」「谁点了确认」全是事实记录，没有一条是平台的判断。冒领的责任在线下沟通的双方。
2. **平台不做站内私信。** 帖子上的联系方式是唯一联系通道，因此**必填**；但**内容不做任何校验**——全凭自觉，用户为自己填的东西负责。（平台一旦开始校验，就要为校验结果背书，这正是原则 1 要避免的位置。）
3. **「认领」不是排他锁，是审计日志。** 任何人都可以解锁任何 found 帖的联系方式，互不阻塞；系统只记录「谁看过」。
4. **只做 lost + found，其余尽量精简。** 判断一个功能该不该加的唯一标准：**它是否直接帮助「一个丢东西的人」和「一个捡到东西的人」联系上**。不是就砍。
   - 推论：**不要设计需要用户填出他其实不知道的信息的字段。** 据此删掉了品牌和颜色两个字段。
   - 第 6 版把「不做举报仲裁」拆成了两件事：**仲裁仍然不做**（原则 1）；**举报要做**，但它只是「有人觉得这条有问题」的事实记录——它是治理的**眼睛**，不是治理的**手**。没有举报，管理员完全是瞎的。
5. **管理员是「数据和系统维护 + 内容与账号治理」的管理员，不是「社区和责任」的管理员。**
   - 分界线不是「有没有副作用」——治理必须有副作用，删了 spam 却不告诉人为什么，他明天接着刷。
   - 真正的分界线是**这个副作用产生的事实是关于谁的**：**admin 能销毁内容和账号，但不能制造归属。**
   - 落地机制三条：① 不存在任何以 admin 身份推进社区流程的端点（#25/#26 对 admin 返回 `FORBIDDEN`，service 层只比 `submitter` 和 `item.user_id`，**根本不看 role**）；② 每个写操作必须填理由并与业务改动**同事务**落 `admin_actions`；③ 「谁做的」写进数据（`reviewer_id` / `review_kind`）。
   - 完整表述：他不为**物品归属**担责（那不是他能判断的事），但他为**自己的治理动作**担责（一条不落，永远查得到）。

## 2. 用户与角色

| 角色 | 定义 | 关键能力 | 明确不能 |
|---|---|---|---|
| **匿名访客** | 未登录的任何校园用户 | 逛广场、关键词搜索、按分类/地点筛选、看帖子全部内容（标题/描述/图片/时间/具体位置）、**直接看到 lost 帖的联系方式** | 看 found 帖的联系方式（锁着）、发帖、解锁、举报 |
| **失主（lost 方）** | 丢了东西的人 | 发 lost 帖、搜索、解锁任意 found 帖的联系方式、提交归还确认（附文字+凭证图）、撤销自己的确认、举报、关自己的帖 | 替别人确认归还 |
| **拾主（found 方）** | 捡到东西的人 | 发 found 帖、查看自己帖子的解锁名单、对别人提交的归还确认**点「确认」或「拒绝」**、举报、关自己的帖 | 给自己的帖子提交归还确认 |
| **管理员** | 平台秩序维护者 | 批量下架 / 恢复 / 删图 / 删违规归还确认 / 警告 / 封号解封 / 改 role / 维护字典 / 处置举报 / 看统计与操作日志 | **任何制造「两个用户之间归属关系」的动作**：confirm、reject、force-close、干预匹配——端点根本不存在 |

同一自然人可以同时是失主和拾主；角色不是身份标签而是每条帖子的属性。`role` 只有 `user` / `admin` 两值，账号状态只有 `active` / `banned` 两值。

> 权限约束的表达方式：**「admin 不能做」不是靠文档约定，是靠「路由不存在」+ 三个遍历测试**（M6：非 admin 打满 `/api/admin/*` 全 403、admin 打满「仅发帖人」路由全 403、路由表里不存在 `admin.*returns.*confirm|reject` 这类路径）。

## 3. 核心场景与用户旅程

### 3.1 主线 A：拾主发 found 帖

小王在图书馆捡到黑色钱包 → 登录 → 发布拾物 → 填 **7 个字段**（标题、描述、分类两级联动、地点三级联动、具体位置、**实际拾获时间** `found_at`、联系方式；图片可选多张）→ 提交。

**发帖成功后系统立刻同步跑一次 Tier 1 匹配**（反向扫 open 状态的 lost 候选）：对每个 score ≥ 0.75 的 lost 帖 L，写一行 `match_pairs`（`ON CONFLICT DO NOTHING`），**只有真的插进去**（说明这一对以前没被通知过）才给 **L 的作者**发一条 `new_match` 通知。

- **小王自己不收任何通知。** 他是被动方，发完帖义务就完成了；lost 方会自己找上门（联系方式锁在他帖子里，对方解锁即可）。
- 响应体只回 `notified_count: 3`——「你这条帖子系统已经推给了 3 个可能丢过东西的人」。这是一条事实，也是一种正反馈。
- **匹配失败只记 error 日志，绝不影响发帖成功。** 匹配是增值功能，不能拖垮主流程。

### 3.2 主线 B：失主找到帖子并解锁联系方式

小李有三种途径，成本从低到高：

| 途径 | 说明 |
|---|---|
| **① 主动搜索（最该先试）** | 广场搜「钱包」+ 地点筛选。未登录可用，零成本、零副作用、立刻有结果。**搜到了直接联系，整条路径根本不需要发 lost 帖** |
| ② 发帖时当场看到 | 他发 lost 帖后，成功页直接列出高分 found 帖（`matches_preview`）——相当于系统替他又搜了一次，且比关键词搜索准 |
| ③ 后来被通知 | 他发帖时库里还没有对应 found 帖；三天后小王发了 found 帖，Tier 1 扫到他，`new_match` 通知找上门 |

**帖子内容对未登录用户完全公开，只有联系方式锁着。** 登录后进帖子 →「认领并查看联系方式」按钮 → 点击 = 往 `contact_views` 登记一次查看，返回联系方式。

- 这一步**不是排他锁**：小张、小刘也能各自解锁，各留一行，谁都不挡谁。「认领」只是 UI 叫法，后端语义是「登记一次联系方式查看」。
- **解锁不产生任何通知**（`contact_unlocked` 已删）。想知道谁看过，发帖人自己去解锁名单页查。
- **lost 帖不走这套**：lost 帖的联系方式直接公开，未登录也能看。理由是丢东西的人巴不得被联系上，而捡到东西的人不想被骚扰——所以只有 found 帖需要解锁。

### 3.3 主线 C：线下联系，三种结局

**结局一 · 确认是他的**：两人私下核对特征、当面归还 → 小李**归还完成后**提交「归还确认」（文字说明 + **至少一张凭证图，必填**）→ 小王收到 `return_submitted` → 看过后点「确认」→ 系统连锁：found 帖 `status → closed`、小王 +10 分、小李 +2 分、`credit_logs` 两行流水、小李收到 `return_confirmed`、反查台账给配对的 lost 帖作者发 `item_returned_hint`（提醒他也去关帖）。

**结局二 · 发现不是他的**：**什么都不用做。** 不点按钮、不取消、不说明。帖子继续 open，`contact_views` 里那行记录留着（它只是查看日志，不代表认领成功），他可以再去解锁别的帖子。这是刻意设计：**平台不做裁决，就不该逼人表态。**

**结局三 · 有人乱提交**：提交归还确认**没有任何前置门槛**（不要求先解锁、不要求匹配过）——任何登录用户都能对任何 open 的 found 帖提交。正因为谁都能提交，**判断真假的权力完全在发帖人手里**：小王点「拒绝」。

> ### ⚠ 全系统最容易误解的一条语义边界
>
> **「拒绝」拒绝的是那条归还确认记录，不是那条帖子。**
>
> - 拒绝**不会**：关帖、扣分、通知提交人以外的任何人、阻止别人重新提交。
> - 拒绝**只会**：把那一行改成 `rejected`（该记录终态）+ 给提交人发一条 `return_rejected`（附发帖人写的说明）。
> - 帖子 `status` **仍然是 `open`**，继续在广场展示、继续参与匹配、继续等下一个人解锁。
> - 语义是「我不是你的东西的主人 / 你没还给我」，不是「这条帖子无效」。
>
> 产品上必须让发帖人明白这一点：拒绝一条假的归还确认，不会伤害这个物品寻找真主人的能力。
> 实现上有专门测试守着（M5 `TestRejectDoesNotCloseItem`）。

### 3.4 主线 D：失主发 lost 帖

**产品层面必须先答的问题：先搜索还是先发 lost 帖？——先搜索。** 这决定了首页长什么样：广场对未登录完全开放，**搜索框是首页最大最显眼的元素**；「发布失物」按钮旁边一行小字「先搜一下，可能已经有人捡到了 →」，点过去是预填关键词的广场；发布表单顶部同样放这条引导。发 lost 帖是**搜不到之后的登记**，价值面向未来。

流程：登录 → 填标题、描述、分类、地点、具体位置、**两个时间**、联系方式、图片 → 提交 → **系统同步跑 Tier 1，把前 5 条 found 帖直接放在响应里**（`data.matches_preview`）→ 成功页展示「我们找到了 3 条可能的拾物帖」+「都没有？那就等一等，之后有人发拾物帖时我们会通知你」→ 归还后小李自己去「我的发布」点「已找到」。

- **两个时间的分工**：`last_seen_at` = 最后一次确认还拿着它（周一 8:00 在食堂还用过）；`lost_at` = 发现它不见了（周二 15:00 摸口袋空的）。**丢失是一个区间，拾获是一个时刻**——这是匹配算法的核心输入。
- **lost 帖创建：一行 `match_pairs` 都不写，一条通知都不发。** 三个理由：① 唯一需要知道的人正在屏幕前，结果直接回给他看就行；② found 方不需要做任何事，通知他只是打扰；③ 丢东西是主动行为，找东西的责任在失主。
- **lost 帖没有归还确认流程**：「确认收到」的人就是发帖人自己，他直接关帖即可。

### 3.5 一条 lost 帖不一定匹配得上，它照样有用

**大多数 lost 帖永远不会匹配成功**（东西没被捡到，或被捡到但那人没发帖）。如果 lost 帖的价值只等于「匹配成功」，这个功能对绝大多数用户就是零。它有三个独立于匹配的价值：

1. **一条公开可搜、联系方式直接可见的记录**——捡到东西的人搜到就能联系，全程不惊动平台任何机制。**这可能是最高频的成交路径。**
2. **未来 found 帖的匹配靶子**——三天后有人发帖，Tier 1 会扫到这条 lost 帖并发通知。lost 帖是「挂在那儿等未来」的，这正是它和「搜一下就完事」的本质区别。
3. **失主自己的追踪清单**（「我的发布」里能看状态、能自己关闭）。

**因此 UI 文案必须诚实**：❌ 不写「发布失物，系统帮你找回」；✅ 写「发一条公开记录：捡到的人能搜到你并直接看到你的联系方式；之后如果有人发拾物帖匹配上了，我们会通知你」。

### 3.6 平台做了什么、没做什么（一页总览）

| 平台**做** | 平台**没做** |
|---|---|
| 存帖子、图片、分类、地点 | 判断谁是真正的主人 |
| 时间地点硬筛选 + 分类文本排序，算出可能匹配 | 裁决两个冲突的认领主张 |
| found 帖创建时把匹配结果通知给 **lost 方** | **通知 found 方任何匹配相关的事**——一条都不发 |
| lost 帖创建时把匹配结果**当场返回给发帖人自己** | 为 lost 帖创建发任何通知 |
| 记录谁解锁过联系方式 | 限制谁可以解锁 |
| 记录归还确认的文字和图片 | 验证归还是否真的发生 |
| 在**发帖人本人**确认时关帖、加信用分 | 让任何其他人（**包括管理员**）点出一次有社区含义的「确认」 |
| 给管理员内容与账号治理能力（下架/删图/警告/封号/改字典/统计） | 给他任何「代表平台裁决」的端点 |
| 要求每个 admin 写操作填理由并逐条留痕 | 让治理动作无痕 |
| 把「谁做的」写进数据 | 让数据修正被误当成发帖人确认 |
| **记录举报** | **仲裁举报**——不判断举报是否成立 |
| 通知被处置的人「你的帖子因 X 被下架」 | 通知**被举报**的人（否则举报立刻变成互相攻击的手段） |
| 发通知 | 提供站内私信 |
| 要求帖子必填联系方式 | 校验联系方式是否真实 |
| 让 lost 帖成为公开可搜的记录 | 保证它一定匹配得上 |

## 4. 功能需求

优先级：**P0** = 产品不成立；**P1** = 核心体验；**P2** = 治理与运维。里程碑是交付批次。接口编号 `#N` 对应计划 §4 的 50 条路由清单（49 个 JSON API + 1 个静态图片路由）。

### FR-1 账号与身份（P0 · M1）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-1.1 | 用户名+密码注册；**重名 409、弱密码 400**（密码 <8 位或纯数字不合格） | 注册响应**不含 token**（注册和登录是两个端点）；`role` 恒为 `user`，请求体无法指定角色 |
| FR-1.2 | 登录签发 JWT（默认 24h 过期），返回 `expires_at` | 「用户名不存在」与「密码错误」响应**完全同形**（防账号枚举） |
| FR-1.3 | 被封禁账号无法登录/操作 | `USER_BANNED` |
| FR-1.4 | 查看/修改自己的资料（昵称、手机、邮箱） | 响应永不含 `password_hash` |
| FR-1.5 | 修改密码需验证旧密码 | 仅本地账号可用（SSO 用户无密码） |
| FR-1.6 | 本地账号密码是**永久一等公民**，不是 SSO 的临时替代 | SSO 当前外部阻塞，且本地登录是唯一不依赖外部服务就能跑通的方式 |

### FR-2 字典：分类与地点（P0 · M2）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-2.1 | **公开只读**的分类树（两级 55 行种子）和地点树（三级 91 行种子） | 未登录也必须能拿到，否则前端三个下拉框渲染不出来 |
| FR-2.2 | 发帖**只能选叶子节点**：分类必须是 level 2、地点必须是叶子 | 选一级大类 / 有子节点的中间层地点 → `VALIDATION` 且 `data.errors` 指到具体字段 |
| FR-2.3 | 「其他」类自由地点（`is_freeform=true`）作为逃逸值存在 | 选它时前端**强制要求填「最近的建筑」**，并显示红色警告「选『其他』会极大降低匹配成功率」 |
| FR-2.4 | 字典树**不缓存**，每次请求直接查库 | 管理员在数据库里手工改名后立刻生效，不需要重启（55+91 行根本不值得缓存） |
| FR-2.5 | admin 增删分类/地点（`#9–#12`，**必填 reason**） | 被帖子引用的项删不掉（`CATEGORY_IN_USE`）；**没有改名端点**——改名走数据库工具（已知能力缺口，见 §10） |

### FR-3 发帖与图片（P0 · M2）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-3.1 | lost / found **共用一张表**，用 `item_type` 区分 | 广场天然混合展示；匹配是同表自配对 |
| FR-3.2 | **表单只有 7 个字段**：标题、描述、分类、地点、具体位置、时间、联系方式（+可选图片）。字段少是这个系统的优点，**不要往回加** | — |
| FR-3.3 | **没有颜色选择器、没有品牌输入框**（两列已删） | 颜色/品牌/外观写进标题和描述；`brand` 用户根本填不出来（不开机不搜索就不知道牌子），而**猜测比空值更有害** |
| FR-3.4 | 时间字段由数据库 CHECK 强制语义正确 | lost 必填 `last_seen_at` + `lost_at` 且前者 ≤ 后者、`found_at` 必须为空；found 必填 `found_at`、另两个必须为空。填错 → `VALIDATION` 且错误同时指向冲突的两个字段 |
| FR-3.5 | **联系方式必填但内容不校验** | 空 / 纯空白 / 全角空格 → `VALIDATION` 且 `field:"contact"`；填「无」「问宿舍阿姨」「13800000000」一律成功。**前端同样不做格式校验**（后端明确放弃了，前端捡回来就是自相矛盾），只有 maxlength=100 和非空 |
| FR-3.6 | 图片上传（≤5MB，jpg/png/webp/gif），一帖多张、有序 | 超限 `FILE_TOO_LARGE`，类型不符 `FILE_TYPE_UNSUPPORTED`；**匿名上传必须 401**（等于给全网开免费图床） |
| FR-3.7 | 帖主可删除自己帖子里的**单张图片**（`#42`） | 图片行删、磁盘文件删、**帖子本身还在**；别人删这张图 → `FORBIDDEN`。这是隐私泄露时最快的自救路径，不用等管理员 |
| FR-3.8 | 编辑 / 软删除 / 关闭状态 | 非本人改他人帖 → `FORBIDDEN`；改自己 `closed` 的帖子**合法**（`ITEM_CLOSED` 只挡 `deleted`）；`status` 三值 `open/closed/deleted` |

### FR-4 广场、搜索与详情（P0 · M2）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-4.1 | 列表**完全公开**，支持 `item_type / keyword / category_id / location_id / status / sort`（可按创建时间、丢失时间、拾获时间排）+ 分页 | 列表里的 found 帖**不带 contact** |
| FR-4.2 | 详情公开，但 contact 按四条规则决定可见性 | ① lost 帖 → 返回；② 发帖人本人 → 返回；③ 已登录且 `contact_views` 有记录 → 返回；④ 其余 → `contact=null` + `contact_locked=true`。响应**始终**带 `contact_locked`，前端据此显示锁图标/按钮/内容 |
| FR-4.3 | 「我的发布」列表（含自己的 contact） | 走 `/api/my/...` 命名空间 |

### FR-5 匹配（P0 · M3）

产品问题：**这条 lost 帖，和库里哪条 found 帖可能是同一个东西？**

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-5.1 | 四步工作法：字典把自由文本变成可比 ID → SQL 硬筛选砍掉绝大部分候选 → Go 里打分排序（**分数只决定顺序，不决定去留**）→ 空手而归时兜底放宽并明确告知用户 | 分类选错、描述写得潦草都不会让物品**消失**，只会排后面 |
| FR-5.2 | **Tier 1（严格）**：地点必须完全相同 + 拾获不早于「最后确认拥有」减 1 天容差 + 只看 open + 排除自身，候选上限 200 | 三个信号打分：分类 **0.45** / 文本 **0.40** / 时间 **0.15** |
| FR-5.3 | 时间信号用满两个时间字段 | `found_at` 落在 `[last_seen_at, lost_at]` 窗口内 → 满分 1.0；晚于 `lost_at` → 14 天线性衰减（**起点是 `lost_at` 而非 `last_seen_at`**，否则周二发现丢、周三捡到的会被无谓压低）；早于 `last_seen_at`（1 天容差内）→ 0.3 重罚但不清零，因为填表会出错 |
| FR-5.4 | 中文文本相似度：字符 **bigram + Dice**，不引分词库 | 归一化后按 **rune** 切（按字节会把中文切碎）；不用单字（「的」「色」满天飞产生大量假高分）；已知缺点：跨词边界的无意义片段（「色钱」）也计分 |
| FR-5.5 | **Tier 2（兜底）**：不做地点硬筛选，时间硬筛选保留，地点降级为排序信号 | 四信号：分类 0.35 / 文本 0.30 / 时间 **0.20** / 地点 0.15。触发条件（任一）：Tier 1 返回 0 条 / 地点是「其他」/ 用户主动点「放宽筛选」。**二元放宽，不做四级渐进**（该方案已被否决） |
| FR-5.6 | 权重次序必须体现「**先分类，再分词**」 | 分类 > 文本 > 时间 > 地点，严格递减。地点在 Tier 1 是硬筛选所以不参与打分 |
| FR-5.7 | 每条结果返回 **`breakdown`**：每个信号的权重、分数和中间值（`title_dice` / `desc_dice` / `days_after_lost_at` / `same_leaf` …） | **这就是匹配调试器**：`0.45*1.0 + 0.40*0.71 + 0.15*0.93 = 0.87` 前端可直接验算，用户能看到「为什么系统认为这两个是一个东西」。**`breakdown` 里不允许有 `attr` 键**（该信号已随颜色/品牌列一起删除，留着会让前端和测试误以为它还存在） |
| FR-5.8 | 阈值：`≥0.75` 高置信 / `0.55–0.75` 仅展示 / `<0.55` 默认不返回（用户可用 `min_score` 放宽） | 阈值和权重是**可配常量**，调参不改代码不改公式 |
| FR-5.9 | **三个触发源，只有一个会写库**（这是通知不对称的落点） | ① found 帖创建 → 写 `match_pairs` + 给 lost 作者发 `new_match` + 回 `notified_count`；② lost 帖创建 → **算完就丢**，回 `matches_preview`（top 5），`notified_count` 不出现；③ `GET /items/:id/matches` → 永远现算，不写不发。`≥0.75` **不等于一定发通知**（同对已通知过则去重跳过） |
| FR-5.10 | `match_pairs` 是**通知台账**，不是匹配结果表 | 只记「系统在某一刻认为这一对足够像，并因此通知过 lost 方」。用途恰好三个：通知去重、confirm 时反查发提示、调参历史。**不能拿它统计命中率**（Tier 2 和 lost 方向根本不写它） |
| FR-5.11 | Tier 2 结果必须带 `tier` 字段 + 提示文案，前端画黄色横幅 | 「没有找到确定的匹配。可能原因：① 还没有人上传/拾到该物品；② 存在一定概率的不匹配。你可以自行调整下方的地点、时间、分类筛选条件。」**Tier 2 不写台账、不发通知**（置信度不够，发通知是打扰） |
| FR-5.12 | 匹配端点需登录，且只有发帖人本人或 admin 可访问 | 匹配结果含另一批帖子的作者昵称和「可能是同一个东西」的推断，匿名请求既非本人也非 admin → `401`，而不是认成匿名后给个空列表 |

### FR-6 联系方式解锁（P0 · M4）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-6.1 | 解锁是 **POST**，不是 GET | 它要往 `contact_views` 写一行事实记录；用 GET 的话浏览器预取、爬虫、任何「顺手访问」都会凭空制造解锁记录，而那份日志正是骚扰事件的**唯一事后证据**，必须只由真实点击产生 |
| FR-6.2 | **幂等 + 非排他** | 同一人重复点只有一行；第二个用户也能解锁成功；**零自动后果**（不通知发帖人、不下沉别人的记录） |
| FR-6.3 | 对 lost 调解锁接口 → `VALIDATION` | lost 帖的联系方式本来就公开，不存在解锁这个动作 |
| FR-6.4 | 对已关闭的帖解锁 → `ITEM_CLOSED` | — |
| FR-6.5 | 解锁名单只有发帖人和 admin 能看（`#22`） | 「谁算发帖人」要先把帖子查出来，所以这个判断住在 service 而不是路由 |
| FR-6.6 | 前端点击后有一句轻提示 | 「认领只是登记，不会阻止其他人联系发布者」——避免用户误以为是排他锁定 |

### FR-7 通知（P0 · M4/M5）

**不对称是这个系统最重要的结构**：写通知的触发路径只有 found 帖创建 + 归还状态流转 + 治理动作三类。

| type | 发给谁 | 触发 |
|---|---|---|
| `new_match` | **仅那条 lost 帖的作者** | found 帖创建且 score ≥ 0.75 且台账新增成功（去重靠 `ON CONFLICT`） |
| `return_submitted` | found 帖发帖人 | 有人提交归还确认 |
| `return_confirmed` | 提交人 | 发帖人点确认 |
| `return_rejected` | **仅提交人** | 发帖人点拒绝 |
| `item_returned_hint` | 配对的 lost 帖作者 | confirm 时反查台账（「你找的东西可能已被领回，去确认一下」） |
| `admin_action` | 被处置的用户 | 治理动作回执（**同作者 N 条合并成 1 条通知**，content 含 admin 填的理由原文） |
| `report_resolved` | **举报人**（不含被举报人） | 举报被处置，含「驳回」结论也要回话 |

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-7.1 | 收件箱 / 未读数 / 标记已读（`{ids:[]}` 或 `{all:true}` 二选一） | 三条全部需登录，「我的」永远来自 JWT 而不是查询参数 |
| FR-7.2 | **两条绝对不发通知的禁令** | ① 解锁联系方式（`contact_unlocked` 已删——非排他解锁会让热门帖产生一堆噪音通知）；② 被举报人永远不知道自己被举报过（否则举报立刻变成骚扰工具和报复性对刷的起点） |
| FR-7.3 | 通知的 `item_id` / `return_id` 只是跳转用，不是外键 | 通知说的是「某件事发生了」这个事实，而那条帖子可能已被删除 |

### FR-8 归还确认（P0 · M5）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-8.1 | **提交没有任何前置门槛**（`RETURN_NOT_UNLOCKED` 整个删除，不是放宽） | 它是平台强加的流程门槛，和「全凭自觉」矛盾，而且会卡住线下先认识、从没在平台上解锁过的双方。只剩三条前提：帖子存在、帖子 open、不是自己的帖子 |
| FR-8.2 | 文字（5–1000 字符）**+ 凭证图（必填）** | 凭证图是唯一能把线下交接和平台帖子对上号的客观证据，可选就等于没有；整个信用分体系就挂在这一步上 |
| FR-8.3 | 一条帖子同时只能有一条 pending（部分唯一索引） | 重复提交 `RETURN_DUPLICATE`；**被拒的那行留在库里当审计痕迹**，提交人可修改后重新提交 |
| FR-8.4 | 状态机：`pending → confirmed / rejected / cancelled`，三个终态 | 非法流转 `RETURN_ILLEGAL_TRANSITION`（如对已 rejected 的记录再 confirm）。终态不可回退——「这条已经表过态了」 |
| FR-8.5 | 只有**发帖人本人**能 confirm/reject，**admin 也不行** | 拒绝也**必填**说明（`owner_note`，随通知发给提交人） |
| FR-8.6 | **拒绝零附带伤害** | 不改帖子状态、不扣分、不通知提交人以外的任何人、不阻止别人重新提交（见 §3.3 语义边界） |
| FR-8.7 | 提交人可在 pending 期间自己撤销 | 零副作用、不发通知 |
| FR-8.8 | 两个列表：我提交的 / 我收到的 | 区别只是 JOIN 出来的那一列，**分页和状态筛选行为必须一模一样** |

### FR-9 信用分（P1 · M5）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-9.1 | 初始 100，边界 [0, 200] | 撞上下界时流水记**实际生效**的增量，不是名义值 |
| FR-9.2 | 唯一加分路径：一次由**发帖人本人**确认的归还 → 拾主 +10、提交人 +2 | 全系统只有这一处加分（+12 是自然结果，不是单独规则）。`Σ流水 + 100 == 当前分` 必须恒成立 |
| FR-9.3 | **拒绝不扣分** | 在「发帖人自审」的语境下，被拒往往只是诚实的误认；扣分会让人不敢提交 |
| FR-9.4 | `admin_data_fix` 类型不加分 | 数据修正不是社区确认 |
| FR-9.5 | 每条变动都有流水（delta / reason / 关联对象） | 只有当前分值的话，「为什么我是 110」解释不了；用户问、客服查、测试对账三件事都要有依据 |
| FR-9.6 | 信用分在提交人信息里展示给发帖人看 | 这是发帖人判断真伪的四项依据之一：文字 + 图片 + 提交人昵称 + 提交人信用分 |

### FR-10 举报（P1 · M4/M6）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-10.1 | 任何登录用户可举报任何帖子，六个 `reason_code`（spam / privacy / fraud / harassment / illegal / other）+ 可选补充说明 | **只支持举报帖子，不支持举报用户**：骚扰实际发生在解锁之后，那条路径已有 `contact_views` 全量记录；举报用户把矛头从内容指向人，容易变成私刑工具 |
| FR-10.2 | **举报是治理的眼睛，不是治理的手：零自动后果** | 不自动下架、不扣分、不影响匹配和广场排序、不通知被举报人。`report` 这条链路上只有一条 INSERT |
| FR-10.3 | 同一人对同一帖只能有一条待处理举报 | `REPORT_DUPLICATE`（部分唯一索引）。这是挡「两个人互相看不顺眼就互相刷举报灌满待办队列」的第一层 |
| FR-10.4 | 多人举报同一帖 = 优先处理信号 | 待办列表带 `report_count_on_item`，次数高的排前面；**这个数字只给 admin 看**，绝不显示在用户自己帖子上（否则变成举报军备竞赛） |
| FR-10.5 | admin 处置：`takedown` / `ban` / `dismiss`，**必带 reason** | `resolution` 只影响处置动作，**不代表平台认定举报成立**。`dismiss` 也不通知被举报人 |
| FR-10.6 | 处置一条举报会连带关掉同帖的所有 open 举报，所有举报人都收到回执 | 它们说的是同一条内容，处置一次就够；不这么做待办队列会一直挂着已处理掉的条目 |
| FR-10.7 | 留痕**按动作计数，不按请求计数** | `takedown` 写 2 行（`report_resolved` + `item_takedown`），`ban` 写 2 行，`dismiss` 写 1 行——「谁驳回的举报」和「谁删的帖子」是两个可以分别追责的问题，合成一行就查不出第二个了 |
| FR-10.8 | 前端**举报入口要弱、文案要诚实** | 详情页右上角一个小的文字按钮（不是醒目红色图标）；提交成功提示必须写「已记录，管理员会看到」，**绝不能写「我们会尽快处理」或「该帖将被下架」**——后端没有任何自动后果，前端承诺了就是骗用户 |

### FR-11 治理与管理后台（P1/P2 · M6）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-11.1 | 内容治理：批量下架 / 恢复 / 删单张图 / 删违规归还确认（有副作用：真的从广场消失、真的发通知） | **批量是刚需**：一次传 50 个 id，一个事务内软删 + 按作者分组发通知 + 写留痕。50 条 spam 点 50 次不现实 |
| FR-11.2 | 账号治理：改 role / 封号解封 / 发警告（有副作用：封了真的登不上、警告真的送到） | 不能降自己的 role、不能封自己 |
| FR-11.3 | 只读：用户列表 / 统计 / 任意帖的匹配与解锁名单 / 任意归还确认 / 操作日志 | 零副作用 |
| FR-11.4 | **每个 admin 写操作必须填 reason，且留痕与业务改动在同一事务** | 不给理由直接 `VALIDATION` **且一条数据都没变**（同事务是 `adminlog` 唯一有意义的性质：日志写不进去业务就回滚）。#16/#17 本来就允许 admin 调用，在 admin 分支上补写日志（决定：不收回权限，补留痕） |
| FR-11.5 | 「谁做的」写进数据 | `item_returns.reviewer_id` + `review_kind`（`owner` / `admin_data_fix` / null）。前端对 `admin_data_fix` 明写「**由管理员数据修正，非发帖人确认**」，不加分、不发「发帖人已确认」通知。**数据自己会说话，不需要靠权限规则去假装** |
| FR-11.6 | 「删了帖不告诉人为什么，他明天接着刷」——治理必须有后果 | 但**不存在**任何以 admin 身份推进社区流程的端点。#16 admin 改帖时**不重跑匹配**（改一个字不该给一堆 lost 用户推通知——那是在替发帖人重新表态） |
| FR-11.7 | 直接改数据库仍是 admin 的合法工具（字典改名、修 2099 年的脏数据这类低频操作） | 从那里改一行，改出来的**只是一行数据**：不会发通知、不会加积分、不会推进状态机——因为那些逻辑在 service 层。他能改事实，但改不出「发帖人同意了」这个**含义**。代价是不落留痕，因此配了一条被动检测 SQL（`status IN ('confirmed','rejected') AND review_kind IS NULL` 命中即证明是在 service 之外写出来的） |
| FR-11.8 | 管理后台五个页签：用户 · 举报待办 · 批量下架 · 操作日志 · 统计 | 批量下架页**理由为空时按钮必须禁用**（让用户先看到「不能提交」比看到「提交失败」好），理由下方预览通知文案；操作日志页存在的意义是**任何 admin 都能看见其他 admin 干了什么，包括他自己昨天干了什么** |

### FR-12 可观测与可调试（P0 · M0–M6）

这不是运维需求，是**产品需求**：「匹配不准」「他没收到通知」这类模糊抱怨必须能落到具体数字上，否则只能靠猜。

| 编号 | 需求 |
|---|---|
| FR-12.1 | 结构化 JSON 日志，字段固定：`time, level, msg, request_id, user_id, method, path, status, duration_ms, err` |
| FR-12.2 | **RequestID 中间件**：每个请求的每条日志和每个错误响应都带它。**报 bug 时给一个 request_id 就能捞出完整链路**——这是整套日志设计的全部目的 |
| FR-12.3 | `LOG_LEVEL=debug` 时输出每条 SQL + 参数 + 耗时 + 影响行数（不熟 SQL 的人学会看自己在执行什么的最直接教材） |
| FR-12.4 | 匹配运行指标**走日志不进表**（`match.run`：tier / fell_back / candidate_count / scored_count / top_score / above_notify / notified_count / duration_ms）。用 `match_pairs` 算这些会得出完全错误的结论 |
| FR-12.5 | 有了日志，「匹配不准」这种最模糊的抱怨就能落地：`candidate_count=0` → 筛选太严（地点没选对/时间填错）；`top_score` 一直很低 → 描述写得太短；`fell_back=true` 占比高 → 大家发帖不选地点 |
| FR-12.6 | 统一响应信封 `{code, message, data, request_id}`；错误码是稳定机器码，**message 是给人看的中文、随时可改**，前端和测试只允许 match `code` |
| FR-12.7 | 未预期错误一律 `INTERNAL`，原始错误只进日志不进响应体（数据库驱动的错误信息里可能带 SQL 片段和连接串） |
| FR-12.8 | 调试入口：健康检查、`breakdown` 匹配调试器、`/api/debug/config`（仅 dev + admin，敏感值打码） |

## 5. 关键业务规则与不变量

这几条是产品的骨架。它们看起来像实现细节，实际是**产品承诺**——违背任何一条，第 1 节的定位就塌了。

| # | 不变量 | 为什么 | 怎么验 |
|---|---|---|---|
| I-1 | **平台不产生任何归属判断。** 全系统唯一能让一次归属成立的动作，是发帖人本人点下 confirm | 原则 1 | admin token 打 #25/#26 必须 403；service 层一次都不读 role |
| I-2 | **通知方向不对称**：匹配相关通知只发给 lost 方，found 方永远收不到匹配通知 | 原则 2/4：拾主是被动方，发完帖义务完成 | 建 found 帖 → lost 作者 +1 条、found 作者 0 条；建 lost 帖 → **两张表都 0 行** |
| I-3 | **解锁和举报这两条路径绝对零通知、零自动后果** | 原则 3、举报≠仲裁 | 解锁后断言 `notifications` 无新增行；举报后断言被举报人通知数 0、帖子 `status` 未变、广场排序未动 |
| I-4 | **拒绝归还确认 ≠ 关闭帖子** | 「没有『认领失败』这个动作」 | `TestRejectDoesNotCloseItem`：reject 之后直接查库，帖子仍是 `open` |
| I-5 | `Σ credit_logs.delta + 100 == users.credit_score`，且加分路径唯一 | 分数必须可解释 | 对账 SQL + 加分路径只有一处的结构性约束（service 装配图上不存在「直接改分」这条路） |
| I-6 | **每个 admin 写操作都留痕，且与业务同事务** | 权力越大越要留痕 | `TestEveryAdminWriteIsLogged`（按**动作**计数：#49 的 takedown/ban 期望 +2）；不带 reason 时业务一条都没变 |
| I-7 | 匹配是增值功能，**任何匹配失败都不得影响发帖成功** | 主流程优先 | 发帖返回 200 且台账写入失败时只记 error 日志 |
| I-8 | 校验失败的请求**不得留下数据行** | 否则「每条错误码都对，但库里堆了一堆不该存在的行」 | 冒烟脚本用 `items` 行数 before/after 相等来断言 |
| I-9 | 联系方式唯一约束是「非空 + ≤100 字符」，**永不做内容校验** | 平台不为自己不担保的东西背书 | 「无」「问宿舍阿姨」必须能发帖 |
| I-10 | `match_pairs` 只由 found 帖创建这一条路径写入 | 它是通知台账，不是结果表 | 三条触发源各自的写库断言（FR-5.9） |

## 6. 非功能需求

| 类别 | 需求 |
|---|---|
| 范围与规模 | 校园规模。不做预计算、不做定时任务、不引入消息队列（收益为零、复杂度三座大山）。候选集每次只有几十条，详情级匹配请求 <10ms，**永远现算**，不需要缓存 |
| 认证安全 | 密码 bcrypt（永不存明文）；JWT 默认 24h 过期；`JWT_SECRET` **必填且无默认值**（给默认值等于给所有部署实例同一把钥匙），缺失启动即失败；**不做限流、不做验证码**（与「不加限制」的定位一致） |
| 隐私 | 已知风险：联系方式实际等于向所有注册用户公开，且 SSO 真实姓名大概率拿不到，威慑力只来自 `contact_views` 审计日志。**当前接受**。若出现骚扰，最小代价补救是给解锁加「每日上限」（一条 SQL 计数，不动表结构），而不是加流程门槛 |
| 上传 | ≤5MB；仅 jpg/png/webp/gif；存本地目录，DB 只存相对路径；**上传目录路径穿越防护**（`../../etc/passwd` 这类值必须被拒绝） |
| 时间 | 一律 UTC 存储，前端展示转本地时区，任何地方不手写时区偏移 |
| 数据完整性 | 软删除优先于物理 DELETE（丢历史、外键连带问题多）；用户名可空 + **部分唯一索引**（SSO 用户没有用户名，强制生成 `hdu_xxxx` 是脏做法） |
| 可测性（硬要求） | **所有关键功能都必须有对应的可 debug 代码和冒烟测试**，不是「功能能跑」。三层：单元测试（不连库）→ 集成测试（临时测试库，代码建库、跑前清空）→ 手工冒烟脚本（打真实运行中的服务和开发库）。集成测试**必须显式要求执行**（带 `REQUIRE_INTEGRATION` 标志），否则「全绿」可能意味着一条集成测试都没跑 |
| 契约稳定性 | 22 个状态码常量（`OK` + 21 个错误码）。**已删除**：`CLAIM_*`、评论相关、`RETURN_NOT_UNLOCKED`。**未启用**：`RATE_LIMITED`。admin 缺 reason **复用 `VALIDATION`**，不新加码。M8 的 3 个 SSO 码现在**不建**，等开工再加 |

## 9. 范围外（明确不做，附原因）

产品范围由定位原则 4 决定：**不直接帮助「丢东西的人」和「捡到东西的人」联系上的，一律砍掉。**

| 不做 | 原因 |
|---|---|
| 站内私信 | 联系方式是唯一通道（原则 2） |
| 留言 / 评论 | 第 4 轮删除，用户明确「留言不做」 |
| 收藏、关注、历史、推荐位 | 同上，原则 4 |
| **认领排他锁** | 原则 3。认领是审计日志不是锁 |
| 颜色 / 品牌字段 + 前端色块选择器 + `?color=` 筛选 + `S_attr` 信号 | 品牌用户填不出来，猜测比空值更有害；颜色要么将来用 YOLO 从图片识别，要么不做。删列不损失信息——bigram 文本相似度本来就能捕捉「黑色」这类连续双字词 |
| **`RETURN_NOT_UNLOCKED` 前置校验** | 平台强加的流程门槛，和「全凭自觉」矛盾，会卡住线下先认识的双方 |
| 联系方式内容校验 / 占位值黑名单 / 真实性校验 / 敏感词过滤 | 原则 2；平台不为自己不担保的东西背书 |
| 限流 / 验证码 | 用户明确不加 |
| 举报自动后果（自动下架 / 降权 / 扣分 / 通知被举报人） | 举报 ≠ 仲裁。加了就变成仲裁，违反原则 1 |
| 举报「用户」（只支持举报帖子） | 矛头从内容转向人，容易变成私刑工具 |
| **admin 的社区裁决能力**（admin confirm / reject / force-close / 干预匹配） | 原则 5。做了就意味着平台在背书 |
| 字典改名端点 | 低频（一年发生不了一两次），为一个 PUT 端点做带审计的接口不值当 → 走数据库工具。已知缺口，见 §10-5 |
| 匹配四级渐进放宽 | 用户否决，保持 Tier 1 / Tier 2 二元 |
| 预计算 / 定时任务 / 缓存匹配 | 校园规模收益为零，复杂度三座大山 |
| 用 `match_pairs` 做统计报表 | 它是通知台账，Tier 2 和 lost 方向根本不写它，拿它算会得出完全错误的结论。可观测性一律走日志 |
| 拿信用分做排序 / 门槛 | 信用分目前只是「诚实记录 + 给发帖人看的判断参考」，不参与任何算法 |

**已删除的接口/概念**（避免从旧设计手滑带回来）：原 claims 全套（#21–#28）、comments 全套、`contact_unlocked` 通知类型、`RETURN_NOT_UNLOCKED` 错误码、`items.color` / `items.brand` 列、`match_pairs.tier` 冗余列、`S_attr` 信号、`breakdown.attr` 键。

## 10. 风险与已知缺口

| # | 风险 | 缓解 / 观察指标 |
|---|---|---|
| 1 | **SSO 双重外部阻塞**：① 凭证需人工申请，无自助注册；② 授权端点对第三方是 302 还是返回 JSON 未知（若只返回 JSON 整个方案作废，需改走学校 CAS） | 本地账号密码做成永久一等公民；`auth.Provider` 接口同时容纳两种实现；M8 阻塞解除前不开工，且不阻塞其他任何进度 |
| 2 | **地点硬筛选太严，Tier 1 长期空转**：91 个精确叶子意味着双方必须选到同一栋楼，而现实里东西会被踢到墙角、被保洁挪走、被好心人带到宿舍 | 观察 `match.run` 日志里 `fell_back=true` 的占比（**不要去查 `match_pairs`，结论会完全错误**）。若占绝大多数，再讨论分级放宽（改动局限在 matcher 和一条 SQL，不动表结构） |
| 3 | **联系方式实际等于向所有注册用户公开** | 已接受。威慑只来自真实姓名 + 解锁审计日志。补救路径是每日解锁上限（一条 SQL 计数），**不是**把流程门槛加回来 |
| 4 | **归还确认可能被乱提交**（提交无前置条件） | 技术防刷只有三条：pending 唯一、凭证图必填、拒绝不加分也不扣分（刷了没收益）。**真正的防线不是技术，是发帖人自己的判断**——平台不裁决，所以也不负责挡住假提交，只负责让发帖人有足够信息自己判断。补救路径是每日提交上限，**不是**加回前置校验 |
| 5 | **字典改名没有接口**（有增删无改，而删又被引用检查挡住），「图书馆三楼」写成「图书馆3楼」之后没有任何接口能改回来 | 已明确决定走数据库手工改。两个操作约束：① 字典树不缓存，否则改完得重启；② 改地点树时别动 `parent_id` 制造环（`items.location_id` 是外键）。真变痛了就补一个带 reason 的 PUT 端点，不动表结构 |
| 6 | **帖子不关闭会污染候选池** | confirm 联动关帖解决大半；lost 靠发帖人手动关；前端在「我的发布」显眼放「已找到/已归还」按钮；`item_returned_hint` 主动提醒；（可选）发帖 N 天后发提醒通知 |
| 7 | **举报被当武器互相刷** | 已挡三层：同人同帖只能有一条待处理、被举报人永无感知、零自动后果（攻击收益为 0）。剩余风险：管理员手滑泄露举报人信息则三层全废（所以 #48 的 `reporter` 只返回昵称且仅 admin 可见）。观察 `GROUP BY reporter_id` 的分布 |
| 8 | **admin 权力过度集中**（一个账号就能下架任何帖、封任何号，没有第二个 admin 需要同意） | 刻意接受。边界是「能销毁，不能制造归属」——他封不掉一场真实交接，也确认不了任何一次归还。**剩下的唯一防线是事后可追责，不是事前制衡**：reason 非空 + 全量留痕 + 操作日志页对所有 admin 可见。这条防线成立与否完全取决于留痕是否和业务同事务 |
| 9 | **匹配完全依赖用户会不会写描述**（两方都只写「钱包」两个字就没法进一步排序，只能靠时间兜底） | 缓解 = U-2 那行文案。将来低成本出路：YOLO 颜色识别作为 `matcher` 之外的独立步骤，结果作为第五个信号传进打分函数——**不需要改表结构**，所以现在不预留 color 列是对的 |
| 10 | **分数分布整体上移导致通知太吵**（删掉 `S_attr` 后，一对原来卡 0.738 的真匹配现在能拿 0.874） | 阈值先沿用 0.75/0.55，M3 打印一批已知真/假匹配的实际分布再决定要不要提到 0.80。**改常量，不改公式、不改权重** |

## 12. 开放问题

以下三条在计划里标注为「不阻塞开工」，本文不代为拍板：

1. **若干小决定按「能跑通 + 精简」先定了，未获明确表态**：`/api/my/...` 命名空间（代价是 URL 不那么教科书 REST）；通知标记已读合并成一个带 body 的 PUT（少一条路由、少一个冲突点）；登录不做限流和验证码；举报只针对帖子；批量下架按作者合并通知；字典树不缓存；留痕按动作而非按请求计数。
2. **`proof_image_path` 是否保持必填** —— 建议保持（唯一能把线下交接和平台帖子对上号的客观证据，且整个信用分体系挂在这一步上，这里松了系统就没有任何硬东西了）。若放宽成「图片或文字至少一项详细」，那么 confirm 时的加分就不该照给。**不表态即按必填实现。**
3. **通知阈值 0.75 是否要调** —— 删掉属性信号后分数分布整体上移，通知量会比上一版多。建议**不要现在拍一个数**：M3 打印真实分数分布之后再决定要不要提到 0.80，因为「多少算像」在这套权重下没有先验答案，看数据比猜快。改一个常量重跑单测即可，不是不可逆决定。

**已定稿、不再是开放问题**（历史上反复改过，记录于此以免重开）：归还确认 `rejected` 的语义（**拒绝记录不拒绝帖子**，2026-10-06 用户原话确认，四节里各有一条断言守着）；管理员边界（改过三版，现「能销毁内容和账号，不能制造归属」，靠全量可归因而非「无副作用」）；治理动作高频做端点、低频走数据库工具；要不要举报（**要，但做最轻的那种：进表、零自动后果、不通知被举报人**）；字典改名（不做接口）；admin 是否保留改删他人帖的权限（**保留，但在 handler 里补写日志**）；通知方向（不对称，只通知 lost 方）；先搜索还是先发帖（先搜索）；`color`/`brand`（删）；contact 校验（只校验非空）；留言评论（不做）。
