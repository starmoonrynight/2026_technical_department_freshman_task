## 0. 一句话结论

杭电助手平台已重构为 **HDUHelp Neo**，旧的 `open-docs` 文档站（`open.hduhelp.com/docs/develop/`）**整体作废**。
真实接口在 `https://api.hduhelp.com/hduhelp-neo/open-apis/` 下，认证模型是 **OAuth2 授权码 + PKCE(S256)**。
第三方接入的唯一阻塞点是：**没有自助注册入口，`app_id` / `app_secret` 必须由杭电助手运营人员手工下发。**

### 1.2 一个必须知道的排查陷阱

旧路径返回 404，但**"404" 在这里不能证明"接口不存在"**，原因有两层：

1. **`*.hduhelp.com` 是通配 DNS。** 实测编造的乱码子域名 `zzq-nonexistent-8f3k2.hduhelp.com` 也解析到同一个 IP `47.110.55.93` ✅，并返回完全相同的 404。
2. **外层 Go mux 对一切未匹配路由回默认 404。** 响应体是纯文本 `404 page not found`，且**响应头里没有 `Server`** ✅。

因此正确的判据是 **`Server` 响应头**：

| 响应特征 | 含义 |
|---|---|
| `Server` 缺失 + `text/plain` + `404 page not found` | 请求打到了外层 mux，**该前缀没有任何路由** |
| `Server: hertz` + JSON | 请求命中了 Neo 应用，**路由存在**，返回的是业务/参数校验错误 |

实测对照 ✅：

```
GET /oauth/token                    → 404  Server=None     text/plain  "404 page not found"
GET /hduhelp-neo/health/config      → 404  Server=hertz    text/plain  "Not Found"
GET /hduhelp-neo/open-apis/authen/authorize
                                    → 400  Server=hertz    application/json  {"error":"invalid_request",...}
```

第二行尤其关键：`/hduhelp-neo/health/config` 本身也是 404，但**带 `Server: hertz`** —— 说明 `/hduhelp-neo/` 这个前缀已经被路由到一个活着的 Hertz（CloudWeGo）应用，只是那个具体子路径不存在。

## 2. 阻塞项：必须先拿到凭证

### 2.1 没有自助注册 📄

对 `openapi.yaml` 全量 479 个操作枚举后确认：**唯一能创建应用的端点是 `POST /hduhelp-neo/admin/apps`，它要求 `OperatorBearerAuth`（运营管理员令牌）**。整个 API 面上不存在任何公开的开发者注册、自助申请或审批入口。

相关端点全部是 operator 权限 📄：

```
POST   /hduhelp-neo/admin/apps                      创建应用
GET    /hduhelp-neo/admin/apps                      列出应用
PUT    /hduhelp-neo/admin/apps                      修改应用
DELETE /hduhelp-neo/admin/apps                      删除应用
PATCH  /hduhelp-neo/admin/apps                      局部修改
PUT    /hduhelp-neo/admin/apps/permissions          改权限
GET    /hduhelp-neo/admin/scopes                    读取完整 scope 目录
```

服务端确实校验 `app_id` 白名单 ✅ —— 实测用编造的 `app_id` 请求授权端点：

```
GET /hduhelp-neo/open-apis/authen/authorize?app_id=cli_zzq_probe&response_type=code
→ HTTP 401  Server=hertz
  {"error":"invalid_client","error_description":"unknown app_id"}
```

**结论：`app_id` 无法猜测或伪造，必须走人工申请。**

### 2.2 申请时需要一次性提供的 4 项 📄

来自 `CreateAppRequestBody` 定义。少报任何一项都要再来一轮，建议一次说全：

| 字段 | 类型 | 说明 |
|---|---|---|
| `name` | string | 应用名称 |
| `redirect_uris` | string[] | **精确匹配白名单**。服务端按绝对 http(s) URL 校验，协议、域名、端口、路径、结尾斜杠都必须一字不差。本地调试地址也要一并报上去 |
| `user_scopes` | string[] | 用户授权范围上限。决定用户令牌（UAT）能请求什么、以及同意页能展示什么 |
| `application_scopes` | string[] | 服务端令牌（TAT）范围。决定你的后端能代用户调哪些接口 |
| `description` | string | 可选 |
| `tenant_key` | string | 可选，单租户场景缺省自动归属默认租户 |

返回：`app_id` 与**一次性明文的 `app_secret`（仅创建那一刻可见，之后不再回显）** 📄。
→ 拿到后必须立即妥善保存，丢了只能重置。

`app_id` 格式为 `cli_` 前缀 📄（SDK README 示例 `cli_xxx`，测试夹具用 `cli_test`）。

生效规则 📄：用户令牌的实际权限 = **用户同意时的 scope 快照 ∩ `apps.user_scopes`**。两者都是实时读取，改配置不需要重新签发令牌。

### 2.3 必须问团队的 2 个问题 ❓

这两个问题公开资料无法回答，但**直接决定失物招领系统能不能做成、怎么做**：

**问题一：`GET /authen/authorize` 对第三方浏览器跳转，到底是 302 重定向还是返回 JSON？**

- 规范里它的响应体是 JSON 结构 `AuthenAuthorizeData { code, redirectUri, state }` 📄
- 但配套端点 `GET /authen/authorize/preview` 的描述是"供一方同意页展示"，且要求 `NativeSessionAuth`（杭电助手自己的登录态）📄
- 参数里有 `consent`（bool，"用户已在一方页面明确同意"）和 `identity_type` 📄

→ 所以**无法确定**第三方直接让用户浏览器访问这个 URL 时，杭电助手会不会渲染自己的同意页然后 302 回你的 `redirect_uri`，还是只吐 JSON（那样就只有杭电助手自己的前端能用，第三方网页登录走不通）。

**这是最高优先级的问题。** 如果答案是"只返回 JSON"，那网页版失物招领系统就没法用杭电助手登录，得改用学校统一身份认证（`sso.hdu.edu.cn`）。

**问题二：怎么拿学号？**

`user-info` 的响应结构里**没有学号字段** 📄：

```
AuthenUserInfoData { userId, name, avatar, scopes[], identityType }
```

规范描述明确写了："**base 身份不会返回学号或校园身份数据**" 📄。

SDK 测试代码里出现过 scope 字面量 `identity:staffid:read` 📄，但没有任何用户信息字段承载它。

→ 失物招领业务如果要按学号认领/登记，必须问清楚：申请哪个 scope、调哪个接口、`identityType` 要传什么值才能拿到学号。
→ 如果拿不到，**用 `userId` 作为本系统的用户唯一键**（它是杭电助手全局 ID，格式类似 UUID）。

### 2.5 关于 PAT（个人访问令牌）—— 不适用于本项目 📄

`hduhelp/cli` 用 RFC 8628 设备码授权换取 PAT。看起来像是一条捷径，但**不能用**：

1. PAT 只认证**它的主人自己**。失物招领系统要认证的是任意来访学生，必须走授权码流程为每个用户签发 UAT。
2. `GET /authen/user-info` 要求 `UATBearerAuth`，**PAT 不被接受** 📄。
3. 全 479 个操作里，声明 `PATBearerAuth` 的只有 **1 个**：`DELETE /hduhelp-neo/cli/tokens/current`（撤销自己的令牌）。
4. 设备码端点规范原文："**仅 hduhelp-cli 客户端可用，不签发 UAT/TAT**" 📄 —— 硬绑定官方 CLI 的 `client_id`，第三方无法复用。

PAT 适合"我自己的脚本查我自己的成绩"，不适合多用户 Web 应用。

## 3. 通用约定

### 3.1 地址

```
Base URL   https://api.hduhelp.com
路径前缀    /hduhelp-neo/
第三方前缀  /hduhelp-neo/open-apis/
```

📄 `core/option.go`：`const DefaultBaseURL = "https://api.hduhelp.com"`
**没有版本段**（不存在 `/v1/`、`/neo/`、`/api/`）📄
仅支持 HTTPS。

### 3.2 不要混淆的三个命名空间 📄

| 前缀 | 用途 | 第三方能用吗 |
|---|---|---|
| `/hduhelp-neo/open-apis/` | **第三方开放接口** | ✅ 这是你要用的 |
| `/hduhelp-neo/identity/` | 杭电助手**自家 App** 的登录接口（45 路径）：`auth/login/password`、`auth/login/sms`、`login/wechat/qr`、`identity/me` 等 | ❌ 大多要求 `NativeSessionAuth` |
| `/hduhelp-neo/admin/` | 运营后台 | ❌ 要求 operator 令牌 |
| `/hduhelp-neo/cli/` | CLI 专用（PAT 管理） | ❌ |

### 3.3 两种错误信封 —— 必须都处理

同一个 base path 下存在**两套不同的错误格式** ✅，这是最容易写错的地方：

**A. OAuth 风格**（`authen/authorize`、`authen/access-token`、`auth/device-authorization` 用）
```json
{"error": "invalid_request", "error_description": "具体说明"}
```

**B. 业务码风格**（`authen/user-info`、`auth/tenant-access-token/internal` 用）
```json
{"code": 40105, "msg": "invalid user access token"}
```

→ 解析响应时要先判断存在 `error` 键还是 `code` 键，不能只写一套。

### 3.4 成功判定

成功响应统一是 `{code, msg, data}` 信封，**`code == 0` 为成功** 📄（`core/token.go`）。

### 3.5 ⚠ HTTP 状态码不可信

实测 ✅：

```
GET /hduhelp-neo/open-apis/authen/user-info
Header: Authorization: Bearer hduhelp_pat_fake

→ HTTP 200 OK                       ← 状态码是 200！
  Server: hertz
  Content-Type: application/json; charset=utf-8
  {"code": 40105, "msg": "invalid user access token"}
```

**令牌无效时返回 HTTP 200，错误藏在 body 的业务码里。**
→ 只判断 `resp.status_code == 200` 会把无效登录当成成功。必须检查 `code == 0`。

（对比：同一个端点**完全不带** `Authorization` 头时返回的是 HTTP 401 `{"code":401,"msg":"missing token"}` ✅。带错误令牌反而是 200。行为不一致，两处都要防。）

### 3.6 鉴权头

三种令牌（用户令牌 UAT / 租户令牌 TAT / PAT）**用的是同一个头格式** 📄（`core/transport.go`）：

```
Authorization: Bearer <token>
```

服务端靠令牌值本身区分类型，不靠头。
旧文档的 `Authorization: token <t>` **已失效** ✅（对应端点整体 404）。

PAT 的字面前缀是 `hduhelp_pat_` 📄。

### 3.7 Content-Type 不一致 📄

| 端点 | Content-Type |
|---|---|
| `POST /authen/access-token` | **`application/x-www-form-urlencoded`** |
| `POST /authen/refresh-access-token` | **`application/json`** |
| `POST /authen/revoke` | `application/json` |
| `POST /auth/device-authorization` | `application/x-www-form-urlencoded` |
| `POST /auth/tenant-access-token/internal` | `application/json` |

→ 换 token 用表单，刷新 token 用 JSON。同族端点不一致，是服务端就这样，接入时别"顺手统一"。

### 3.8 PKCE 规则 📄（`core/pkce.go`）

```
code_verifier  = base64url_nopad(32 字节随机数)          → 43 字符
code_challenge = base64url_nopad(SHA256(ASCII(verifier)))
code_challenge_method = "S256"                            → 固定值
```

`base64url_nopad` = URL-safe base64 且**去掉末尾 `=` 填充**。

### 3.9 令牌生命周期 📄

- `expiresIn` 单位是**秒**
- `refresh_token` **一次性、每次刷新轮换**，必须持久化保存最新那个，用旧的会失败
- 租户令牌约 7200 秒

### 3.10 本地开发环境注意 ✅

Windows 控制台默认 `cp1252`，Python 脚本里 `print` 中文会直接抛 `UnicodeEncodeError` 崩溃（实测撞到过）。运行前设置：

```
set PYTHONIOENCODING=utf-8
```

或在代码开头重配 `sys.stdout`。Linux/macOS 无此问题。

## 4. 接口契约

第三方登录只涉及 5 个端点，全部在 `/hduhelp-neo/open-apis/` 下，规范里 tag 均为 `IdentityService` 📄。

### 4.1 获取授权码

```
GET https://api.hduhelp.com/hduhelp-neo/open-apis/authen/authorize
```

鉴权：`public_or_native_session` 📄

**请求参数（query）** 📄

| 参数 | 必填 | 说明 |
|---|---|---|
| `app_id` | ✅ | 申请到的应用 ID |
| `response_type` | ✅ | 固定 `code` |
| `redirect_uri` | ✅ | 必须在白名单内，精确匹配 |
| `scope` | ✅ | **逗号分隔**（注意不是 OAuth2 标准的空格分隔） |
| `state` | ✅ | 自己生成的随机串，防 CSRF，回调时要校验一致 |
| `code_challenge` | ✅ | PKCE，见 §3.8 |
| `code_challenge_method` | ✅ | 固定 `S256` |
| `consent` | ❓ | bool，"用户已在一方页面明确同意" |
| `identity_type` | ❓ | `base` 或某个已绑定的校园身份。规范原文："base 始终可选；非 base 身份必须已绑定" |

**成功响应** 📄（**未实测**）

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "code": "<一次性授权码>",
    "redirectUri": "<回调地址>",
    "state": "<原样返回>"
  }
}
```

**实测到的失败响应** ✅

| 场景 | HTTP | Body |
|---|---|---|
| 完全不带参数 | 400 | `{"error":"invalid_request","error_description":"'appId' field is a 'required' parameter, but the request body does not have this parameter 'appId'"}` |
| `app_id` 不在注册表 | **401** | `{"error":"invalid_client","error_description":"unknown app_id"}` |

> 注意上面第一条：query 参数名是 `app_id`（snake_case），但报错信息里说的是 `appId`（camelCase）。服务端内部字段名和对外参数名不一致，看报错时别被绕晕。

⚠ **本端点最大的不确定性**：响应体是 JSON 而非 302，见 §2.3 问题一。

---

### 4.2 换取访问令牌

```
POST https://api.hduhelp.com/hduhelp-neo/open-apis/authen/access-token
Content-Type: application/x-www-form-urlencoded
```

**请求参数（form body）** 📄

| 参数 | 必填 | 说明 |
|---|---|---|
| `grant_type` | ✅ | `authorization_code`（第三方登录用这个）<br>或 `urn:ietf:params:oauth:grant-type:device_code`（CLI 设备码用） |
| `app_id` | ✅ | |
| `app_secret` | ✅ | **只在服务端调用，绝不能出现在前端** |
| `code` | ✅ | §4.1 拿到的一次性授权码 |
| `code_verifier` | ✅ | PKCE 原文，服务端用它校验 challenge |

**成功响应** 📄（**未实测**）—— 注意字段是 **camelCase**

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "accessToken": "...",
    "refreshToken": "...",
    "expiresIn": 7200,
    "scope": "a:b:read,c:d:read",
    "tenantKey": "...",
    "tokenType": "Bearer",
    "userId": "...",
    "patId": "..."
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `accessToken` | string | 用户访问令牌（UAT），调 §4.3 用 |
| `refreshToken` | string | 一次性，刷新后轮换 |
| `expiresIn` | int64 | **秒** |
| `scope` | string | **逗号分隔**的已授权范围 |
| `tenantKey` | string | 租户标识 |
| `tokenType` | string | 固定 `Bearer` |
| `userId` | string | 用户唯一 ID —— **建议作为失物招领系统本地用户表的外键** |
| `patId` | string | |

> ⚠ 设备码授权（`grant_type=...device_code`）走的是**同一个端点**，但响应是**不带 `data` 包裹的裸对象 + snake_case**：`{access_token, token_type, expires_in, scope, pat_id, code, msg}` 📄。同一个 URL 两种响应结构，解析时要按 `grant_type` 分支。

**实测到的失败响应** ✅

| 场景 | HTTP | Body |
|---|---|---|
| 空表单 | 400 | `{"error":"invalid_request","error_description":"'grant_type' field is a 'required' parameter, but the request body does not have this parameter 'grant_type'"}` |

```json
    "userId": "...",
    "name": "张三",
    "avatar": "https://...",
    "scopes": ["contact:user.id:read"],
    "identityType": "base"
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `userId` | string | 用户唯一 ID |
| `name` | string | 姓名 |
| `avatar` | string | 头像 URL |
| `scopes` | string[] | 本次实际授权的范围 |
| `identityType` | string | 授权时选择的身份类型 |

**没有学号字段** —— 见 §2.3 问题二。

规范原文 📄："凭 `Authorization:Bearer <user_access_token>` 返回用户基本信息及授权时选择的 identity_type，受令牌 scope 约束。**base 身份不会返回学号或校园身份数据。**"

**实测到的失败响应** ✅

| 场景 | HTTP | Body |
|---|---|---|
| 完全不带 `Authorization` 头 | **401** | `{"code":401,"msg":"missing token"}` |
| 带无效的 Bearer 令牌 | **200** ⚠ | `{"code":40105,"msg":"invalid user access token"}` |

## 5. 完整登录时序

```
浏览器/用户            你的后端                      杭电助手 Neo
    |                     |                              |
    | 1. 点"用杭电助手登录" |                              |
    |-------------------->|                              |
    |                     | 生成 state + PKCE verifier    |
    |                     | （verifier 存 session）        |
    | 2. 302 到授权页      |                              |
    |<--------------------|                              |
    | 3. 打开授权 URL       |                              |
    |---------------------------------------------->     |
    |              4. 用户登录 + 选择身份 + 同意授权         |
    | 5. 回调 redirect_uri?code=xxx&state=xxx             |
    |<----------------------------------------------     |
    |-------------------->|                              |
    |                     | 6. 校验 state 一致             |
    |                     | 7. POST access-token          |
    |                     |    (code + code_verifier       |
    |                     |     + app_id + app_secret)     |
    |                     |----------------------------->|
    |                     | 8. accessToken/userId          |
    |                     |<-----------------------------|
    |                     | 9. GET user-info (Bearer)      |
    |                     |----------------------------->|
    |                     | 10. name/avatar/userId         |
    |                     |<-----------------------------|
    |                     | 11. 用 userId 查/建本地用户     |
    |                     |     签发自己的会话              |
    | 12. 登录成功          |                              |
    |<--------------------|                              |
```

**安全要点**
- `app_secret` **只能出现在后端**，绝不能进前端代码或小程序包
- `state` 必须在第 6 步严格校验，不匹配立即拒绝（CSRF 防护）
- `code_verifier` 在第 2 步生成后要存进用户 session，第 7 步取用；不能存 cookie 明文让前端带
- `code` 是一次性的，且很快过期
- 第 11 步：拿到 `userId` 后签发**你自己系统的会话**，不要拿杭电助手的 `accessToken` 当你自己的登录态到处传

## 6. 数据结构（语言无关）

技术栈未定，这里只给字段契约，落地时按语言映射即可。

```
AuthenAuthorizeData {
    code         : string    // 一次性授权码
    redirectUri  : string    // camelCase
    state        : string
}

AuthenTokenData {
    accessToken      : string
    refreshToken     : string
    expiresIn        : int64     // 秒
    scope            : string    // 逗号分隔
    tenantKey        : string
    tokenType        : string    // "Bearer"
    userId           : string
    patId            : string
}

AuthenUserInfoData {
    userId        : string
    name          : string
    avatar        : string
    scopes        : string[]
    identityType  : string
}

// 成功信封
Envelope<T> {
    code : int        // 0 == 成功
    msg  : string
    data : T
}

// 错误信封 A（OAuth 风格）
OAuthError {
    error             : string   // invalid_request | invalid_client | ...
    error_description : string
}

// 错误信封 B（业务码风格）
BizError {
    code : int        // 非 0
    msg  : string
}
```

⚠ **命名风格陷阱**：请求参数是 snake_case（`app_id`、`grant_type`、`refresh_token`），响应字段是 camelCase（`accessToken`、`redirectUri`、`userId`）。设备码响应又是 snake_case 裸对象。三种混用，序列化配置别一刀切。

## 8. 其他已知信息

### 8.1 用户令牌能调的接口只有 3 个 📄

全 479 个操作中，声明 `UATBearerAuth` 的仅 3 个：

1. `GET /hduhelp-neo/open-apis/authen/user-info` — 获取用户信息
2. `GET /hduhelp-neo/academic/student-history/class-members` — 按班级查询历史学生名单
3. `GET /hduhelp-neo/academic/student-history/major-info` — 获取学生历史专业信息

→ **第三方用户令牌的能力面非常窄**，基本就是"确认这个人是谁"。失物招领系统需要的业务数据都得自己存，别指望从杭电助手拉。

### 8.2 租户令牌（TAT）模式 📄

如果拿到的是服务端令牌而非用户令牌：

```
POST /hduhelp-neo/open-apis/auth/tenant-access-token/internal
Content-Type: application/json
{"app_id": "...", "app_secret": "..."}

→ {"code":0,"msg":"...","data":{"tenantAccessToken":"...","expire":7200,"tenantKey":"..."}}
```

注意字段是 `expire`（秒）而**不是** `expiresIn`。
用 TAT 调用业务接口时，必须用 **`X-Staff-Id`** 请求头指定目标用户（该头在规范里出现 40 次）。

对失物招领系统来说这条路径大概率用不上（它是"服务端代查某个学生"，不是"学生自己登录"），列在这里备查。

### 8.3 已确认存在的 scope 字面量 📄

权威清单在 `GET /hduhelp-neo/admin/scopes`（需 operator 权限），拿不到。以下是从规范描述、README、测试夹具里能确认的字面量：

```
contact:user.id:read
identity:staffid:read
academic:grade:read
academic:schedule:read
academic:studenthistory:read
academic:freshmanadmission:read
academic:gradedirectory:read
knowledge:search:read
upload:file:write
```

⚠ **不要硬编码未经团队确认的 scope** —— 申请时让对方给准确清单。
